# Prompt Reliability Evaluation Harness: Design Document

*Markdown version of [Prompt_Reliability_Design_Doc.docx](Prompt_Reliability_Design_Doc.docx).*

## Problem Statement

We observed flaky and inconsistent answers on near-duplicate queries. A user asking the same question with a typo, different phrasing, or extra context sometimes gets a materially different answer. This harness quantifies that drift so we can catch regressions before they reach users.

## Design Decisions

### 1. Why OpenAI gpt-4o-mini as the default model?

**Decision:** Default to gpt-4o-mini, configurable via `--model` flag.

**Rationale:** For a consistency harness that makes 90+ API calls per run (10 cases x 3 variants x 3 runs), cost and speed matter more than raw capability. gpt-4o-mini is fast, cheap (~$0.15/1M input tokens), and still representative of production behavior. The `--model` flag lets us swap to gpt-4o or any other model for comparison runs.

### 2. Why JSON for test cases (not YAML, not Python fixtures)?

**Decision:** Plain JSON file with a flat schema.

**Rationale:** JSON is parseable without extra dependencies, diffable in PRs, and readable by any tool. YAML would add PyYAML as a dependency for marginal readability gains. Python fixtures would make test data harder to inspect without running code. The schema is simple enough that JSON's verbosity isn't a problem at 10 cases.

### 3. Why two separate metrics: Consistency vs. Regex Score?

**Decision:** Report both, interpret them together.

**Rationale: these measure different things:**

- **Regex score** = "Did the model get the right answer?" (correctness)
- **Consistency score** = "Did all variants produce the same text?" (stability)

A case can score regex=1.00 (always correct) but consistency=0.33 (worded differently each time). That's fine for factual Q&A but dangerous for a pipeline that parses the output. Reporting both lets teams decide what threshold matters for their use case.

### 4. Why invariance AND perturbation tests?

**Decision:** Include both types with an `expected_behavior` field.

**Rationale:**

- **Invariance tests** (paraphrase, typo, noise) catch fragility — the answer should NOT change.
- **Perturbation tests** (reorder, distractor, framing) characterize sensitivity — the answer MAY change, and we want to know how often.

Both are needed. A model that's robust to typos but susceptible to anchoring bias (or vice versa) has a very different risk profile. The `expected_behavior` field in test data keeps this distinction at the data level, not in code.

### 5. Why semantic scoring via OpenAI embeddings (not sentence-transformers)?

**Decision:** Use OpenAI's text-embedding-3-small for semantic similarity.

**Rationale:** Since we already depend on the OpenAI SDK and have an API key, using their embeddings avoids adding an 80MB model dependency (sentence-transformers + PyTorch). One fewer install step, one fewer thing to break. The embedding quality is comparable for our use case (comparing short responses to reference anchors).

### 6. Why temperature=0.0?

**Decision:** All API calls use temperature=0.0.

**Rationale:** We're measuring prompt-level consistency, not sampling variance. Temperature>0 would introduce randomness that masks the signal we care about. If a team wants to characterize temperature sensitivity, they can do a sweep as a separate experiment (see Ship Later).

## Test Case Design

### Synthetic Cases (5) — Generation Rules

Each synthetic case was generated by applying a single, explicit transformation rule to a baseline prompt:

| Rule | What it does | Example |
|---|---|---|
| Paraphrase | Reword the question 3 ways, preserving semantic meaning | "What is the capital of France?" -> "Tell me France's capital city." |
| Typo | Swap/drop/duplicate 1-2 characters in key words | "largest" -> "largets", "the" -> "teh" |
| Noise | Prepend/append non-semantic tokens (dashes, filler, random strings) | "--- Convert 100 celsius... ---" |
| Reorder | Shuffle multiple-choice option positions | Options A-D shuffled, correct answer stays Jupiter |
| Distractor | Prefix with a factual sentence containing a number/date | "The Treaty of Westphalia was signed in 1648. What year did WW2 end?" |

### Real-World Edge Cases (5) — Sources (Redacted)

These are anonymized versions of failure patterns observed in production-like scenarios:

| Case | Origin Pattern |
|---|---|
| Code-switch | Support tickets from different user personas (formal engineer vs. casual user) producing different quality answers |
| Framing | Product FAQ where "benefits of X" vs. "drawbacks of not X" yielded contradictory advice |
| Persona | Adaptive learning platform where system prompt changes caused factual drift, not just tone changes |
| Formatting | Document parsing pipeline where whitespace variations caused extraction failures |
| Anchoring | Pricing recommendation system where context numbers biased numerical estimates |

## Scoring Approach

### Metrics

| Metric | Formula | What it tells you |
|---|---|---|
| Exact match | `response.lower().strip() == expected.lower().strip()` | Binary correctness for short-answer cases |
| Regex match | `re.search(pattern, response) != None` | Flexible correctness — tolerates surrounding text |
| Semantic similarity | Cosine similarity of OpenAI embeddings | Content overlap for open-ended responses |
| Consistency | `modal_count / total_responses` | How often the most common answer appears across variants |
| Flip rate | `responses_differing_from_baseline / total_variant_responses` | How often a perturbation changes the answer vs. baseline |

### Interpreting Results

- **Invariance, consistency=1.0, regex=1.0:** The model is robust to this variation. No action needed.
- **Invariance, consistency<1.0, regex=1.0:** Correct but unstable wording. Fine for human-facing; risky for parsed outputs.
- **Invariance, regex<1.0:** The model gives wrong answers for some variants. Real bug — investigate the failing variant.
- **Perturbation, flip_rate=0.0:** The perturbation has no effect. The model is robust to this distractor/reorder/framing.
- **Perturbation, flip_rate>0.5:** The perturbation reliably changes the answer. Decide if that's acceptable.

## Sample Results

gpt-4o-mini, 3 runs per variant, temperature=0

| Case | Type | Consistency | Regex | Flip Rate |
|---|---|---|---|---|
| syn-inv-paraphrase-01 | invariance | 0.67 | 1.00 | — |
| syn-inv-typo-01 | invariance | 1.00 | 1.00 | — |
| syn-inv-noise-01 | invariance | 0.44 | 1.00 | — |
| syn-pert-reorder-01 | perturbation | 0.33 | 1.00 | 1.00 |
| syn-pert-distractor-01 | perturbation | 0.67 | 1.00 | 1.00 |
| real-inv-codeswitch-01 | invariance | 0.11 | 1.00 | — |
| real-pert-framing-01 | perturbation | 0.17 | 1.00 | 1.00 |
| real-pert-persona-01 | perturbation | 0.17 | 1.00 | 1.00 |
| real-inv-formatting-01 | invariance | 0.67 | 1.00 | — |
| real-pert-anchoring-01 | perturbation | 0.67 | 1.00 | 0.50 |
| **OVERALL** | | **0.49** | **1.00** | |

**Key takeaways from the run:**

- Regex = 1.00 across the board — gpt-4o-mini always gets the right answer, regardless of variant.
- Low consistency scores are expected for open-ended responses (different wording, same substance).
- Anchoring bias test shows 50% flip rate — the model's numerical estimates shift depending on context numbers.

## Ship First vs. Later

### Ship Now

- 10 test cases + Python runner + exact/regex scoring + consistency table
- Enough for CI regression detection: run on prompt changes, fail if consistency drops below threshold

### Ship Later (prioritized)

1. Auto-generated test variants (reduces manual authoring)
2. Statistical significance with N=10+ runs and bootstrap CIs
3. Result persistence and trend tracking (JSONL/SQLite)
4. Async API calls for larger test sets
5. Temperature sweep experiments
6. Multi-model comparison matrix
7. GitHub Action for PR-level consistency checks

## How to Run

```bash
# Install
pip install -r requirements.txt

# Smoke test (1 run, fast)
python run_eval.py --runs 1

# Full evaluation
python run_eval.py --runs 3 --output results.json

# Different model
python run_eval.py --runs 3 --model gpt-4o --output results.json

# Specific scorers only
python run_eval.py --runs 3 --scorers regex,semantic
```
